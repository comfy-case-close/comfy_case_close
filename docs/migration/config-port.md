# Configuration port from dev

`GET /api/v1/config` returns the effective settings for the `X-Branch-Id` branch. `PUT /api/v1/config` accepts a full or partial JSON object with the same uppercase keys and writes branch overrides. The caller must have live `CONFIG_WRITE` permission for that branch. Values resolve in `BRANCH > BUSINESS > GLOBAL` order from the existing `platform.app_config` table; there is no second singleton config table. The existing audit trigger records edits.

`GET /api/v1/config/business` returns the business defaults over global values, excluding branch overrides. `PUT /api/v1/config/business` upserts BUSINESS rows for the authenticated tenant; it takes the same partial JSON body and requires the existing business-scoped `BUSINESS_UPDATE` permission. Neither business route uses `X-Branch-Id`. The same permission applies whether it was granted before or after deployment. A branch-only `CONFIG_WRITE` grant does not authorize this route. A BRANCH row still wins over a changed BUSINESS value until its override is removed.

Example: `PUT /api/v1/config`, `X-Branch-Id: <uuid>`, body `{"REQUIRE_APPROVAL_REFUND":true,"REQUIRE_APPROVAL_STAFF_PARKING":false}`. These keys are boolean; monetary thresholds are nonnegative integers. Bank-instruction strings must be nonblank when written. Unspecified settings retain their effective value.

The five `REQUIRE_APPROVAL_*` switches control **separate movement review before close approval**. When a switch is true, a pending movement in that category blocks `POST /api/v1/cash-closes/{id}/approve` until a reviewer decides that movement. When false, the close reviewer approves that pending movement in the same transaction before approving the close. This line decision has its own audit entry. Pending movements outside the five mapped categories always need separate review. Rejected movements are already decided and do not block close approval. For example, with refund=true and staff parking=false, an undecided refund blocks the close, while an undecided staff-parking line is approved together with the close.

At submission, `REQUIRE_POS_IMAGE` requires a `POS_REPORT` attachment; `REQUIRE_CASH_IMAGE` requires `CASH_DRAWER_PHOTO`; and a configured `DIFF_NOTE_REQUIRED_ABS` requires a note when the unexplained difference reaches that amount. `REQUIRE_EXPENSE_RECEIPT_IMAGE` requires an expense movement to carry a `receiptFileId`. `REQUIRE_UNPAID_BILL_REPAYMENT` requires a `TRANSFER_PROOF` file for an `UNPAID_BILL` movement, either as the movement's `receiptFileId` or attached to the close, including one added after submission. A one-step submission passes close-level files as `attachments: [{"fileId":"<uuid>"}]` and movement receipts as each movement's `receiptFileId`. The file kind is read from `files.stored_file`. Existing file upload APIs create the `fileId` first.

Existing `DIFF_ALLOWED_ABS`, `DIFF_ALERT_ABS`, and `FUND_WITHDRAWAL_WARNING_ABS` still feed their prior calculation/warning paths. The remaining dev settings are exposed and persisted, but have no additional cash-close behavior: dev itself did not consume the expense/withdrawal alert thresholds, suggested cash remaining, bank-instruction strings, or session TTL in those flows. They are available to clients or a future owner of those policies. The existing global `REQUIRE_POS_IMAGE=true` remains in force, so submitting clients must send a POS report attachment or an authorized user must set a branch override to false.
